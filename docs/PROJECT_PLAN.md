# Scketch Relay 제작 계획

실행 환경과 서버 구성은 [ENVIRONMENT.md](./ENVIRONMENT.md)를 참고한다.

## 1. 프로젝트 목표

Scketch Relay는 여러 사용자가 하나의 방에 모여 문장과 그림을 번갈아 전달하고, 마지막에 완성된 릴레이를 함께 감상하는 웹 게임이다.

### MVP 목표

- 별도 설치 없이 브라우저에서 이용한다.
- 방 코드 또는 초대 링크로 2~8명이 참여한다.
- 문장 작성과 그림 그리기를 번갈아 진행한다.
- 모든 라운드가 끝나면 처음부터 마지막까지의 결과를 공개한다.
- 모바일, 태블릿, PC에서 사용할 수 있다.

완료 기준:

구현 결과:

- 라우트 파일은 화면 조합만 담당하고, 랜딩 전용 컴포넌트는 `src/components/home`에 배치한다.

- 순수 함수 단위 테스트는 Node.js 내장 테스트 러너로 실행한다.
- 2026-08-21 기준 lint, 테스트 4개, production build가 통과했다.

구현 결과:

- 데이터 저장은 Supabase PostgreSQL, 실시간 알림과 접속 상태는 Supabase Realtime을 사용한다.
- 모든 DB 조회와 변경은 Next.js Route Handler에서 처리하며 참가 권한은 HttpOnly 쿠키로 검증한다.

- 방장이 나가면 가장 먼저 참가한 사용자에게 방장 권한을 이전하고, 마지막 사용자가 나가면 방을 삭제한다.
- 대기실에서는 참가자끼리 자유롭게 채팅하고, 게임이 시작되면 새 메시지 전송을 잠근다.
- 채팅은 참가 쿠키를 서버에서 검증하고 메시지 길이와 연속 전송을 제한한다.
- 코드 구현과 lint, 테스트 6개, production build는 통과했다.
- Supabase 프로젝트 `hjkcqlmfzpuoatgjurhp`를 서울 리전에 생성하고 마이그레이션을 적용했다.
- 서로 다른 두 HTTP 세션으로 방 생성, 참가, 참가자 목록 동기화, 방장 시작과 `playing` 상태 전환을 검증했다.
- 방 참가자 간 채팅 전송과 상대 화면 조회를 검증하고, 게임 시작 후 전송 요청이 `409`로 차단되는 것을 확인했다.

### 3단계 — 게임 진행

목표: 문장과 그림을 번갈아 작성하는 핵심 게임 흐름을 완성한다.

#### 3-1 — 게임 설정과 첫 문장

- 방장은 대기 중 최대 인원(2~8명), 라운드 시간(60/90/120초), 공개 방식(방장 진행/자동)을 변경한다.
- 최대 인원은 현재 참가자 수보다 작게 설정할 수 없다.
- 게임 시작 시 참가자마다 하나의 릴레이를 만들고 첫 문장 제출 기한을 기록한다.
- 참가자는 자신의 첫 문장을 한 번만 제출하고 전체 제출 현황을 확인한다.
- 모든 데이터 변경은 참가 쿠키와 방장 권한을 Route Handler에서 검증한다.

완료 기준:

- 서로 다른 두 사용자 세션에서 설정 변경, 게임 시작, 첫 문장 제출이 동작한다.
- 방장이 아닌 참가자의 설정 변경과 중복 제출이 차단된다.
- 새로고침 후에도 제출 여부와 제출 인원이 복구된다.

#### 3-2 — 그림판과 릴레이 전달

- 첫 문장 제출이 모두 끝나면 서버가 그림 라운드로 자동 전환한다.
- 참가 순서를 한 칸씩 회전해 각 참가자에게 다른 사람의 릴레이를 배정한다.
- 그림 작성자는 배정된 직전 문장만 확인할 수 있다.
- 그림판은 펜 색상, 굵기, 지우개, 전체 지우기와 마우스·터치 입력을 지원한다.
- 그림은 MVP 동안 PNG Data URL로 저장하며 요청 크기를 제한한다.

완료 기준:

- 두 사용자에게 서로의 첫 문장이 교차 배정된다.
- 두 사용자 모두 그림을 제출하면 방이 결과 공개 대기 상태로 전환된다.
- 배정되지 않은 릴레이 내용은 게임 API 응답에 포함되지 않는다.

#### 3-3 — 전체 라운드 진행과 복구

- 문장 라운드에서는 배정된 직전 그림만 보여주고 해당 그림을 설명하는 문장을 받는다.
- 참가자 수만큼 문장과 그림 라운드를 반복한 뒤 결과 공개 대기 상태로 전환한다.
- 제한 시간이 끝난 미제출 항목은 서버가 기본 제출물로 채워 게임이 멈추지 않게 한다.
- Realtime 신호를 놓쳐도 주기적 동기화와 새로고침으로 현재 라운드·제출 상태를 복구한다.

완료 기준:

- 3명 게임에서 문장→그림→문장 흐름이 끝까지 진행된다.
- 각 참가자는 현재 배정된 직전 제출물 하나만 볼 수 있다.
- 제한 시간이 지난 라운드는 다음 API 조회 시 한 번만 자동 마감된다.

- [x] 게임 설정 추가: 인원, 라운드 시간, 공개 방식
- [x] 첫 문장 작성 화면 구현
- [x] 그림판 구현: 펜, 색상, 굵기, 지우기, 전체 지우기
- [x] 그림을 보고 문장을 작성하는 화면 구현
- [x] 제한 시간과 제출 상태 표시
- [x] 제출 완료 후 대기 화면 구현
- [x] 플레이어별 릴레이 순서 배정
- [x] 새로고침 및 일시적 연결 끊김 복구

완료 기준:

- 2명 이상이 문장과 그림 라운드를 끝까지 진행할 수 있다.
- 각 사용자는 이전 단계의 결과만 보고 다음 결과를 제출한다.
- 모든 참가자가 제출하거나 시간이 끝나면 다음 라운드로 이동한다.

### 4단계 — 결과 공개

목표: 완성된 릴레이를 재미있게 함께 감상할 수 있게 한다.

#### 4-1 — 릴레이 결과 공개

- 방장 진행 방식은 방장이 버튼을 누를 때마다 다음 릴레이 하나를 모든 참가자에게 공개한다.
- 자동 공개 방식은 게임 완료와 동시에 전체 릴레이를 공개한다.
- 각 릴레이는 최초 작성자와 문장·그림의 작성 순서를 함께 보여 준다.
- 공개 상태는 DB에 저장하고 Realtime으로 동기화해 모든 참가자가 같은 결과를 본다.

완료 기준:

- 방장 외 참가자의 다음 결과 공개 요청은 차단된다.
- 두 사용자 화면에서 공개된 릴레이 개수와 내용이 일치한다.
- 자동 공개 방식에서는 전체 결과가 즉시 표시된다.

#### 안정성 보강 — 참가자 이탈과 방장 이전

- 게임·결과 화면은 인증된 heartbeat를 10초마다 보내 마지막 접속 시각을 갱신한다.
- 30초 이상 heartbeat가 없는 방장은 다음 활동 중인 참가자에게 권한을 이전한다.
- 게임 중 나간 참가자 레코드와 릴레이는 삭제하지 않고 `중도 이탈` 상태로 보존한다.
- 중도 이탈자의 현재·이후 차례는 기본 제출물로 즉시 채워 남은 참가자가 기다리지 않게 한다.
- 모든 참가자가 동시에 나간 방의 자동 정리는 운영 스케줄러 도입 단계에서 처리한다.

완료 기준:

- 방장 heartbeat 중단 후 활동 중인 참가자가 새 방장이 된다.
- 게임 중 나간 참가자의 차례 때문에 라운드가 멈추지 않는다.
- 게임 화면에서 온라인·연결 끊김·중도 이탈 상태를 확인할 수 있다.

#### 4-2 — 결과 저장·공유와 다시 하기

- 공개된 전체 릴레이를 브라우저 Canvas에서 하나의 PNG 이미지로 만든다.
- Web Share API를 지원하는 기기는 이미지 파일을 공유하고, 미지원 환경은 PNG 다운로드를 제공한다.
- 방장은 결과 공개 완료 후 중도 이탈자를 제외한 멤버로 같은 방을 다시 대기 상태로 전환한다.
- 이전 게임·제출·채팅은 새 게임 시작 전에 삭제하며 참가 쿠키와 설정은 유지한다.

완료 기준:

- 전체 결과 PNG가 문장과 그림을 포함해 저장된다.
- 다시 하기는 방장만 실행할 수 있고 활동 참가자가 2명 미만이면 차단된다.
- 다시 하기 후 모든 활동 참가자가 같은 대기실로 이동한다.

- [x] 릴레이 결과를 순서대로 공개하는 화면 구현
- [x] 방장이 다음 결과 공개를 제어하는 기능 구현
- [x] 전체 결과 한눈에 보기 구현
- [x] 이미지 저장 또는 공유 기능 구현
- [x] 같은 멤버로 다시 하기 구현
- [x] 새 게임과 방 나가기 동작 구현

완료 기준:

- 모든 참가자가 같은 결과와 공개 순서를 본다.
- 결과를 다시 확인하거나 새 게임을 시작할 수 있다.

#### 5-2 — 모바일 조작과 접근성

- 그림판은 터치 그리기 중 페이지 스크롤을 막고, 작은 화면에서도 색상·굵기·지우개를 44px 이상의 조작 영역으로 제공한다.
- 게임 방법 모달은 열릴 때 내부로 포커스를 이동하고 Tab 순환, Escape 닫기, 닫은 뒤 호출 버튼으로 포커스 복귀를 지원한다.
- 모든 대화형 요소에 키보드 포커스 표시를 제공하고 모션 감소 설정을 존중한다.
- 타이머와 제출 현황처럼 변하는 정보는 화면 읽기 도구에 과도하게 반복되지 않도록 의미 있는 시점에 안내한다.

완료 기준:

- 320px 너비 화면에서 가로 스크롤 없이 게임 설정과 그림 도구를 조작할 수 있다.
- 모달 밖으로 키보드 포커스가 빠져나가지 않고 닫은 뒤 원래 버튼으로 돌아온다.
- 그림판에서 손가락과 펜 입력이 페이지 스크롤과 충돌하지 않는다.
- 키보드 포커스와 모션 감소 스타일이 전역에서 일관되게 적용된다.

#### 5-3 — 핵심 API 흐름 자동 테스트

- Node.js 내장 테스트 러너와 독립된 쿠키 세션 두 개로 실제 Next.js API를 호출한다.
- 방 생성·참가·설정·게임 시작·랜덤 제시어 제출·그림 제출·결과 공개·재시작을 한 흐름으로 검증한다.
- 방장이 아닌 참가자의 설정 변경과 재시작, 랜덤 제시어 변조 요청이 차단되는지 확인한다.
- 성공과 실패 여부에 관계없이 테스트가 만든 참가자와 방을 정리한다.

완료 기준:

- `npm run test:integration` 한 번으로 전체 2인 게임 흐름을 재현한다.
- 서로 다른 제시어 배정, 상대 릴레이 전달, 결과 내용과 재시작 상태를 자동 검증한다.
- 테스트 완료 후 Supabase에 테스트 방이 남지 않는다.

#### 5-1 — 시작 방식 안내와 랜덤 제시어

- 자유 문장 모드는 원작의 단어 카드 대신 참가자가 직접 첫 문장을 만든다는 차이를 게임 방법에 명시한다.
- 랜덤 제시어 모드는 게임 시작 시 서버가 참가자마다 서로 다른 제시어를 배정한다.
- 랜덤 제시어는 첫 라운드에서 읽기 전용으로 보여 주고, 제출 API에서도 서버에 저장된 값을 사용해 클라이언트 변조를 막는다.
- 두 모드 모두 첫 문장 이후에는 직전 결과 하나만 보고 그림과 문장을 번갈아 작성한다.
- OpenAI API를 호출하지 않고도 반복 플레이가 가능하도록 검수된 상황형 제시어를 200개 이상 코드에 포함한다.

완료 기준:

- 방장이 대기실에서 자유 문장 또는 랜덤 제시어 모드를 선택할 수 있다.
- 랜덤 모드의 두 참가자에게 서로 다른 제시어가 표시되고 제출 내용도 배정값과 일치한다.
- 게임 방법에서 원작과 현재 웹 게임의 차이, 인원에 따라 마지막 결과가 문장 또는 그림일 수 있음을 확인할 수 있다.
- 정적 제시어는 중복 없이 200개 이상이며 모두 첫 문장 길이 제한을 만족한다.

## 4. 핵심 데이터 초안

구현 전에 다음 데이터 구조를 확정한다.

- `Room`: 방 코드, 상태, 방장, 생성 시각, 게임 설정
- `Player`: 식별자, 닉네임, 접속 상태, 참가 순서
- `Game`: 현재 라운드, 제한 시간, 진행 상태
- `Relay`: 최초 작성자와 문장·그림 제출물의 연결 순서
- `Submission`: 작성자, 종류(문장 또는 그림), 내용, 제출 시각
- `ChatMessage`: 방, 작성자, 메시지 내용, 작성 시각
