# Scketch Relay 제작 계획

실행 환경과 서버 구성은 [ENVIRONMENT.md](./ENVIRONMENT.md)를 참고한다.

## 1. 프로젝트 목표

Scketch Relay는 여러 사용자가 하나의 방에 모여 문장과 그림을 번갈아 전달하고, 마지막에 완성된 릴레이를 함께 감상하는 웹 게임이다.

### MVP 목표

- 별도 설치 없이 브라우저에서 이용한다.
- 방 코드 또는 초대 링크로 2~8명이 참여한다.
- 문장 작성과 그림 그리기를 번갈아 진행한다.
- 모든 라운드가 끝나면 처음부터 마지막까지의 결과를 공개한다.
- 모바일, 태블릿, PC에서 사용할 수 있다.

### 1단계 — 프로젝트 기반 정리

- [x] 랜딩 화면을 작은 컴포넌트로 분리
- [x] 공통 버튼, 입력창, 알림 UI 정의
- [x] 게임에서 사용할 타입 정의
- [x] 환경 변수 예시 파일 작성
- [x] 기본 테스트 구조와 오류 처리 방식 결정

완료 기준:

- 랜딩 화면의 동작이 유지된다.
- 공통 타입과 UI를 다른 화면에서도 재사용할 수 있다.
- `npm run lint`와 `npm run build`가 통과한다.

구현 결과:

- 라우트 파일은 화면 조합만 담당하고, 랜딩 전용 컴포넌트는 `src/components/home`에 배치한다.
- 재사용 UI는 `src/components/ui`, 게임 타입은 `src/types`, 순수 비즈니스 로직은 `src/lib`에 배치한다.
- 예상 가능한 입력 오류는 반환값과 상태 메시지로 처리한다.
- 예상하지 못한 렌더링 오류는 App Router의 `error.tsx` 경계에서 복구 UI를 제공한다.
- 순수 함수 단위 테스트는 Node.js 내장 테스트 러너로 실행한다.
- 2026-08-21 기준 lint, 테스트 4개, production build가 통과했다.

### 2단계 — 온라인 방과 대기실

목표: 사용자가 실제 방을 만들고 다른 사용자가 참가할 수 있게 한다.

- [x] 실시간 통신 및 데이터 저장 방식 결정
- [x] 중복되지 않는 방 코드 생성
- [x] 방 만들기 API 또는 서버 액션 구현
- [x] 방 코드와 닉네임으로 참가하기 구현
- [x] 초대 링크 복사 기능 구현
- [x] 대기실 참가자 목록 실시간 동기화
- [x] 방장 권한과 게임 시작 기능 구현
- [x] 존재하지 않는 방, 가득 찬 방, 중복 닉네임 오류 처리
- [x] 대기실 실시간 채팅과 게임 시작 후 채팅 잠금

완료 기준:

- 서로 다른 브라우저 두 개에서 같은 방에 입장할 수 있다.
- 참가자 입장과 퇴장이 대기실에 반영된다.
- 방장만 게임을 시작할 수 있다.

구현 결과:

- 데이터 저장은 Supabase PostgreSQL, 실시간 알림과 접속 상태는 Supabase Realtime을 사용한다.
- 모든 DB 조회와 변경은 Next.js Route Handler에서 처리하며 참가 권한은 HttpOnly 쿠키로 검증한다.
- 브라우저의 테이블 직접 조회는 RLS로 차단하고 Realtime에는 변경 알림만 전달한다.
- 방장이 나가면 가장 먼저 참가한 사용자에게 방장 권한을 이전하고, 마지막 사용자가 나가면 방을 삭제한다.
- 대기실에서는 참가자끼리 자유롭게 채팅하고, 게임이 시작되면 새 메시지 전송을 잠근다.
- 채팅은 참가 쿠키를 서버에서 검증하고 메시지 길이와 연속 전송을 제한한다.
- 코드 구현과 lint, 테스트 6개, production build는 통과했다.
- Supabase 프로젝트 `hjkcqlmfzpuoatgjurhp`를 서울 리전에 생성하고 마이그레이션을 적용했다.
- 서로 다른 두 HTTP 세션으로 방 생성, 참가, 참가자 목록 동기화, 방장 시작과 `playing` 상태 전환을 검증했다.
- 방 참가자 간 채팅 전송과 상대 화면 조회를 검증하고, 게임 시작 후 전송 요청이 `409`로 차단되는 것을 확인했다.

### 3단계 — 게임 진행

목표: 문장과 그림을 번갈아 작성하는 핵심 게임 흐름을 완성한다.

#### 3-1 — 게임 설정과 첫 문장

- 방장은 대기 중 최대 인원(2~8명), 라운드 시간(60/90/120초), 공개 방식(방장 진행/자동)을 변경한다.
- 최대 인원은 현재 참가자 수보다 작게 설정할 수 없다.
- 게임 시작 시 참가자마다 하나의 릴레이를 만들고 첫 문장 제출 기한을 기록한다.
- 참가자는 자신의 첫 문장을 한 번만 제출하고 전체 제출 현황을 확인한다.
- 모든 데이터 변경은 참가 쿠키와 방장 권한을 Route Handler에서 검증한다.

완료 기준:

- 서로 다른 두 사용자 세션에서 설정 변경, 게임 시작, 첫 문장 제출이 동작한다.
- 방장이 아닌 참가자의 설정 변경과 중복 제출이 차단된다.
- 새로고침 후에도 제출 여부와 제출 인원이 복구된다.

- [x] 게임 설정 추가: 인원, 라운드 시간, 공개 방식
- [x] 첫 문장 작성 화면 구현
- [ ] 그림판 구현: 펜, 색상, 굵기, 지우기, 전체 지우기
- [ ] 그림을 보고 문장을 작성하는 화면 구현
- [ ] 제한 시간과 제출 상태 표시
- [ ] 제출 완료 후 대기 화면 구현
- [ ] 플레이어별 릴레이 순서 배정
- [ ] 새로고침 및 일시적 연결 끊김 복구

완료 기준:

- 2명 이상이 문장과 그림 라운드를 끝까지 진행할 수 있다.
- 각 사용자는 이전 단계의 결과만 보고 다음 결과를 제출한다.
- 모든 참가자가 제출하거나 시간이 끝나면 다음 라운드로 이동한다.

## 4. 핵심 데이터 초안

구현 전에 다음 데이터 구조를 확정한다.

- `Room`: 방 코드, 상태, 방장, 생성 시각, 게임 설정
- `Player`: 식별자, 닉네임, 접속 상태, 참가 순서
- `Game`: 현재 라운드, 제한 시간, 진행 상태
- `Relay`: 최초 작성자와 문장·그림 제출물의 연결 순서
- `Submission`: 작성자, 종류(문장 또는 그림), 내용, 제출 시각
- `ChatMessage`: 방, 작성자, 메시지 내용, 작성 시각
